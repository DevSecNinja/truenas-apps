## Scope and Interpretation

The read-only inventory contains **57 distinct registry/repository families and 100 literal `image:` entries**, across **44 Compose files/overrides, 39 of which contain image entries**. A supplementary non-image inspection found **one remote-source-built container**, `gatus-sidecar`: **101 container definitions in total**. No `.yml` Compose files were found; Immich's hardware-acceleration `extends` files contain no additional images or builds. Counts include repeated service definitions, init containers, sidecars and helper images. They are not running-container counts; an override inheriting an image does not create another literal reference. OpenArchiver is excluded.

The initial 90-day research window is **2026-06-29 through 2026-09-27**, ending at the cutoff above. Older context is labelled per family: mature native releases; slower base/Arr maintenance; retired component histories; Excalidraw's May publication/fix; draw.io's November 2025 base replacement; OpenArchiver's September 2025 manual dependency update; and echo's Actions history back to April 2024. Each widened window explains the historical support, build or release question it answers. Older events are not presented as recent activity; sparse release history alone does not show neglect.

Public source repositories, build definitions, dependency changes, CI results, release records, publisher mappings and registry metadata were examined. Selected [application/utility](#application-and-utility-publishers) and [home-automation/media](#home-automation-and-media) assessments include public manifests, image configuration and SBOM/provenance metadata; exact-pin versus tag-observation limits are stated per group. [Database/supporting-image](#database-and-supporting-image-publishers) and [LinuxServer](#linuxserver-images) findings did not independently resolve our registry pins; LinuxServer's inventories/reports describe observed publisher builds. No layers were pulled, containers executed, production state/secrets/data accessed, deployments changed or runtime tools installed. **No publisher signatures were cryptographically verified.**

**Source snapshot is not released-image provenance.** Permanent code links identify the inspected upstream snapshot, often its then-current main branch; they do not prove that configuration or dependency set was used to build our older pinned release. Tag aliases such as `latest`, `beta`, `7.4-alpine` and `9-alpine` do not establish the source version inside a pinned digest. DHI can also patch packages independently of the application's displayed version.

Of the 100 literal `image:` entries, all except **the two `dhi.io/playwright:1.63.0-debian13` references** have a digest. The separate `gatus-sidecar` build has neither an image tag/digest nor a pinned Git build revision. The linked baseline Compose files and displayed line numbers preserve each exact tag/digest without repeating all digest strings here. A digest fixes artifact identity, not freshness, provenance or safety. Registry index and architecture-specific child digests must not be compared as equivalent identities.

### Assessment and Confidence

| Assessment          | Meaning                                                                                                                                                                                         |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Strong evidence** | Substantive maintenance activity is demonstrated, including actual dependency integration and executed tests where cited. It is not a claim that every dependency or image digest was verified. |
| **Partial**         | Some maintenance mechanisms or activity are evidenced, but important dependency classes, test execution, release linkage or publisher responsibilities remain unresolved.                       |
| **Unknown**         | Public evidence is insufficient to assess the relevant maintenance claim. Access failures and missing public records belong here, not automatically under neglect.                              |
| **Concerning**      | A specific, evidenced process or support gap warrants action. The gap must be described; absence of a bot alone is insufficient.                                                                |

Confidence applies to the stated finding: **high** means direct source/publisher records support it; **medium** means coverage or attribution is incomplete; **low** means substantial uncertainty remains. A high-confidence unknown can mean the public evidence boundary is well established.

| Classification                      | Meaning and limit                                                                                                                                                                                                                            |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A: our pin behind**               | Demonstrated version/pin lag behind maintained upstream or publisher. A newer version alone does not prove our digest lacks a particular fix.                                                                                                |
| **B: source-to-image delivery gap** | Released source or a documented source/build fix exists, but the corresponding image channel demonstrably lags or fails. Requires source and publication evidence, with channel differences stated; not inferred merely from newer versions. |
| **C: maintenance gap**              | A concrete maintenance-process or support gap is evidenced. Not inferred from no Renovate/Dependabot file, low commit volume or a mature native release cadence.                                                                             |
| **D: insufficient evidence**        | The particular claim, often exact fix-to-digest or executed-test linkage, cannot be established publicly. Can coexist with A.                                                                                                                |

These classifications are not exhaustive: **current; no lag established** is valid, not automatically D. D is used only for a specified unknown. Excalidraw/draw.io B findings have dated source and failed-publication evidence; Spottarr's B is narrower, concerning known dependency updates delivered to `main` but not stable `1.20.0`. None implies a particular locally exploitable vulnerability. Distro backports can maintain older versions; fresh tags, clean scans, advertised SBOMs and configured CI jobs do not by themselves establish tested, fixed artifacts.

### What Counts as Maintenance Evidence

An assessment follows **dependency change → executed tests → release → publisher rebuild → exact image**, recording where that chain stops. Coverage includes language packages, vendored native libraries, runtime/toolchain, base OS packages and GitHub Actions. Renovate/Dependabot configuration is useful only within its actual managers and paths; manual imports, distro security tracking and scheduled vendor updates can be equivalent processes.

Lockfiles, source checksums and frozen installs are recorded separately. A lockfile's existence does not prove the release build enforced it; pinned source archives plus mutable `apt`/`apk` packages are not a bit-for-bit reproducible image. Security reporting routes, supported release lines/EOL and SBOM/signature/provenance claims are assessed separately from update cadence.
